# Internationalization

The interface uses i18next and react-i18next. Messages live in
`src/i18n/locales/*.json`; components access translation, number formatting and
diagnostics through `useLocale()`. Keep locale-specific branches out of
components and pass structured data rather than translated text into core code.

## Add a locale

1. Create a JSON file named with a BCP 47 language tag, such as `fr.json` or
   `pt-BR.json`, in `src/i18n/locales`.
2. Set `label` to the language's own name, `direction` to `ltr` or `rtl`, and add
   `messages` using the existing keys and interpolation parameters.
3. Translate complete sentences. Preserve parameters and provide plural forms
   such as `_one` and `_other` for the target language. Avoid assembling sentences
   from translated fragments in JSX.
4. Run type checks, unit tests and the relevant browser tests. Check long messages,
   map controls and mobile layouts. Right-to-left locales need layout testing even
   though the document's `dir` attribute is set automatically.

Vite discovers locale files and populates the selector at build time. No component
or language union needs updating. Resources are bundled with the application.

`en.json` defines typed message keys and fallback text. Add stable, descriptive
keys there first; editing a message does not require renaming its key. Other
locales can be completed incrementally, with missing messages falling back to
English. Unit tests check message keys, interpolation parameters, locale discovery
and fallback behavior.

## Selection and formatting

Selection checks the saved preference, then the browser's language list, trying
an exact region tag before the base language and finally English. The preference
is stored in `localStorage`. If storage fails, switching still works for the
current session. Document `lang` and `dir` follow the selected locale.

Use i18next's `count` for plural selection. `{{count, number}}` and
`useLocale().number()` format numbers for the selected locale. Display units do
not change core calculation units. React escapes interpolated values; translations
must not contain rendered HTML.

## Diagnostics and user data

Import warnings and processing issues use `code + params`, translated at the UI
boundary. Known core codes are listed in `src/core/diagnostics.ts`. Each new
diagnostic needs both an `issues.CODE` message and an
`issues.title.CODE` title. If required parameters are unavailable, the title
provides a localized fallback. Unknown diagnostics and low-level exceptions may
retain their original message. Reports include the structured diagnostics and
rendered explanations in the selected language.

Limits in messages use interpolation defaults from `src/i18n/policy.ts`, derived
from the shared processing policy. Keep these values out of translated text.

Route names, station names and user-entered text are data and remain unchanged
when the locale changes. Switching locale must not regenerate route identity or
change RTE bytes or revisions; browser tests cover this requirement.
